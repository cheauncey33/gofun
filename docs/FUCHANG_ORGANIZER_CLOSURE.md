# Gofun：主办方可运营闭环

本阶段解决“后端有票务接口，但主办方只能靠脚本录入数据”的问题。入口为
`/organizer`，登录后只展示当前用户拥有有效成员关系的主办方。

## 当前闭环

```text
平台管理员创建主办方并指定负责人
→ 负责人进入主办方工作台
→ 创建场馆
→ 创建活动草稿
→ 配置一个场次
→ 配置一个或多个票档
→ 发布活动并预热 Redis 票额
→ 购票站展示活动
→ 主办方查看已支付票数、金额和近期订单
```

活动创建被拆成四步：基础信息、场次场馆、票档、发布。中途关闭后，活动保留为
`draft`，可以从活动表的“继续配置”恢复。第一版每场活动先配置一个场次，避免在
工作台尚未稳定时提前引入多场次编辑器。

## 新增接口

- `GET /api/v1/organizers/mine`
- `GET /api/v1/organizers/:organizer_id/overview`
- `GET /api/v1/organizers/:organizer_id/orders`

工作台其余写操作复用第一阶段已有的场馆、活动、场次、票档和发布接口。所有主办方
接口仍通过 `organizer_member` 校验成员关系，不信任前端传入的主办方 ID。

## 统计口径

- 售票中活动：`event.status = published`
- 已支付票数：只汇总 `ticket_order.status = paid` 的订单项数量
- 已收款金额：只汇总 `paid + payment_status=paid` 的订单金额
- 待支付订单：只统计 `pending_payment`，不包含瞬时 `queued`

## 迁移清理

`AutoMigrate` 现在只包含用户与票务运行所需模型。商品、旧订单、旧秒杀等源码仍然
保留用于回滚，但全新数据库不再自动创建这些遗留表。已有数据库中的旧表不会被自动
删除，避免启动过程产生破坏性行为。

遗留 `uni_user_phone` 索引只在实际存在时删除，不再每次启动都输出 MySQL 1091。

## 明确未包含

- 活动基础信息编辑与下架
- 多场次编辑器
- 主办方成员邀请和复杂权限
- 财务结算、发票与对账
- 电子票、二维码和现场核销

电子票与核销必须作为下一阶段单独建模，不能直接把订单状态当作入场凭证。
