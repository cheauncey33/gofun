# GoFun 压测面试问答

## 一分钟介绍

我用 k6 对抢票链路做了阶梯压测、优化前后对照、短高峰和持续压测，也补了售罄、重复下单、限流和部分故障场景。

因为下单是异步处理，我把接口受理速度和后台订单确认速度分开统计。HTTP 返回成功只表示订单和 Outbox 已落库，后台还要经过消息投递、Consumer 处理和库存确认。我同时看 HTTP P95/P99、实际确认单数、待确认积压、事务提交耗时和数据库连接等待，最后再核对订单、Inbox 和 Redis/MySQL 库存。

在单应用 2 CPU/1GB、MySQL 2 CPU/2GB的测试配置下，完成了 150 单/秒持续 25 分钟的测试，总计 228,501 单全部最终确认，HTTP P99 约 162ms。中途 500 请求/秒的十秒高峰产生约 2,600 单待确认积压，恢复到 150/秒后约 26 秒消化到正常水平。这轮验证了持续受理和短时削峰能力，尚未证明 500/秒可以长期持续。

## 1. 压测具体怎么实现？

用 k6 发真实 HTTP 请求，PowerShell 编排独立 Docker Compose 测试环境，Node 脚本准备用户和活动夹具，并做结果核对。

每次请求带 JWT 和幂等键，检查 HTTP 状态及业务响应码。普通容量测试使用新幂等键，每次成功受理对应新订单；重复下单场景专门复用幂等键，检查重复响应是否只生成一笔订单。

应用暴露 Prometheus 格式的指标，测试脚本定期采样 /metrics、RabbitMQ 队列状态、MySQL 状态和行锁等待信息。每轮停止输入后继续观察，等工作队列及 Outbox 清空，再核对数据库、库存和看板，避免只记录请求阶段而漏掉后台排队。

本次指标分析使用脚本采样，HTTP 分位数来自 k6，订单确认分位数来自应用直方图；不需要依赖 Grafana 截图得出实验结论。

| MySQL | 1 实例，CPU 上限 2 核，内存上限 2GB |

这些是同一台机器上的容器限制，不是每个组件拥有独占物理核心。压测端也在同一 Docker 主机上，共享主机资源与 I/O。这是个人项目的可复现测试环境，不能直接外推生产多机容量。

## 3. 你怎么控制压力？QPS 和并发数有什么区别？

主要使用 k6 的 constant-arrival-rate，按计划每秒启动指定数量的请求。阶梯测试是 100、200、300、400 请求/秒，每档持续 120 秒。

请求速率表示每秒进入多少请求；并发数表示同时有多少请求正在执行。相同的输入速率下，响应越慢，需要的并发越多。所以我配置预分配 VU 和最大 VU，同时检查 dropped_iterations，确认压测端有没有把计划压力实际发出去。

固定 VU 模式下，响应变慢会导致每个 VU 发下一次请求更晚，实际输入速率下降；固定到达率更适合观察队列增长和系统承压，但必须确认压测端资源足够。

## 4. dropped_iterations 是服务器限流吗？

不是。它表示压测工具没有足够的空闲 VU 执行计划中的请求，这些请求没有到达后端。

服务端限流是请求已经到达后端，然后返回 429，单独计入限流拒绝。售罄、限购、服务端异常、网络错误也分别统计，不能把所有非成功响应都合成一个数字。

之前 200 档复测出现 643 次未发出的请求，说明那轮没有完整施加目标压力，因此不能称为稳定承受 200 请求/秒。

## 5. 测试数据怎么准备？有没有把登录开销排除？

抢票容量测试批量准备用户、真实活动和库存，预先签发测试 JWT。每次抢票仍然走应用的 JWT 验证、权限和业务校验，但这轮不包含登录注册过程。

阶梯测试准备 1 万用户、20 万库存；25 分钟持续测试准备 5 万用户、50 万库存，单用户限购仍为 20，订单超时设为 60 分钟。这样可以避免用户限购、售罄或测试期间自动关单干扰容量测量。

登录、注册和其他查询接口放在另一个混合流量场景中测试。登录场景使用真实密码校验；抢票容量测试与混合业务测试分别解释。

## 6. MQ 已经异步了，为什么还看后台吞吐？

HTTP 受理和后台确认是两种能力。MQ 允许入口短时间比 Consumer 更快，缓冲高峰并让后台逐步消化，但长期输入超过处理能力时，等待时间会不断增加。

我分别记录三类结果：接口受理速度和 HTTP 延迟；真实订单确认速度和事务耗时；高峰积压、确认等待时间及高峰后的消化时间。

因此短高峰出现积压是预期行为。持续压测则要观察积压是否不断增长，不能只看 HTTP 返回很快就说系统处理得很快。

## 7. 你怎么计算确认吞吐和积压？

确认吞吐统计订单真正从 queued 迁移到 pending_payment 并提交的次数。重复投递或 Inbox 去重成功不会再次算成新确认订单，避免用消息 ACK 数冒充订单吞吐。

普通容量场景中每次成功受理对应一笔新订单，待确认量按新增受理订单数减真实确认订单数计算。Outbox 和 MQ 的数量用于定位积压位置，不直接相加，因为同一条业务消息可能同时出现在两个观察口径中。

重复下单场景有多次成功幂等响应，不能直接把 HTTP 200 次数当作新增订单数，最终以真实订单和库存变化核对。

## 8. 延迟怎么测？P99 是精确的吗？

HTTP 延迟由 k6 在客户端记录，P99 是这批实际请求中 99% 请求耗时不超过的值，它不是最大耗时。

订单确认延迟从 queued 订单的创建时间计到 Consumer 确认提交后，覆盖订单落库、Outbox、MQ 排队和 Consumer 事务等过程。应用把耗时写入 Prometheus 直方图，再由计数差值计算分位数，所以确认 P99 是桶内插值估计。

限流场景单独统计成功受理的延迟，防止快速返回的 429 把总体 P99 拉低，掩盖真正下单请求的延迟。

## 9. 优化前后怎么保证可比？

保留优化前和当前版本的 Docker 镜像及镜像 ID。在相同资源上限、连接池总预算、Publisher 数、库存分桶和持久化设置下，交替执行前后版本，最后复测 200 档。

每轮创建新活动，前一轮排空后再开始，并保存原始结果。阶梯测试的数据库会积累历史订单，因此缓存、数据规模及运行顺序仍可能影响结果；不能声称已经排除了全部干扰。

这次前后对照比较的是一组改动，不能从总收益中精确拆出每个改动的贡献。单个优化的收益还需要只改变一个因素的实验。

## 10. 实际做了什么优化？效果如何？

主要有三项：

1. Outbox 发布成功后，原来逐条更新状态，现在把一批已收到 MQ 确认的消息 ID 合并为一次 UPDATE，减少状态写入的小事务和提交次数。
2. Consumer Worker 从 6 调到 12，每笔订单仍是独立事务。
3. 合并订单明细和座位凭据查询，减少一次普通凭据读取的数据库往返，保留必要的业务校验。

300 请求/秒档位中，实际确认速度从约 128 单/秒提高到约 250 单/秒。基线积压主要在 Outbox 发布侧，当前版本发布速度能跟上约 300/秒，主要积压转到消费侧。

这个数字是该档位的确认吞吐，不表示已证明可以长期稳定处理 250 单/秒。200 档初轮通过，复测却出现 HTTP P99 3.64 秒和未发出的请求，所以后续又做了持续测试。

Outbox 等待 MQ 确认原本就在数据库事务外，本次优化不能描述为把网络等待新移出事务；合并的是发布成功状态更新，也没有把多笔订单合成一个 Consumer 事务。

## 11. 长时间压测得到了什么结论？

150/s 持续 25 分钟，中途插入 500/s、持续 10 秒的高峰。入口限流放宽，让高峰真正进入下单链路。

| 指标 | 结果 |
|---|---:|
| 实际请求与最终确认订单 | 228,501 |
| 受理成功率 | 100% |
| 未发出请求、服务端异常、传输异常 | 均为 0 |
| 全程 HTTP P95 / P99 | 70ms / 162ms |
| 最差一分钟 HTTP P99 | 400ms |
| 高峰待确认峰值 | 2,591 单 |
| 高峰后恢复正常积压 | 约 26 秒 |
| 全程订单确认 P99，含高峰排队 | 约 7.11 秒，直方图估计 |

本轮证明了该配置下 150/s 持续受理与确认，以及十秒高峰的缓冲和恢复。最终订单、Inbox、各库存桶和看板一致。500/s 只是短时受理能力，不能说是持续确认容量。

## 12. 怎么定位瓶颈，而不是看到 MQ 堆积就猜？

先看积压在哪里，再看该阶段的资源和耗时。

基线发布速度约 128/s，Outbox 持续堆积；优化后发布速度能跟上约 300/s，但实际确认只有约 250/s，MQ 开始堆积，说明主要限制转到了消费侧。再看 Consumer 阶段耗时，而不是看到 MQ 堆积就直接增加消费者。

持续测试中，Consumer 事务平均约 41ms，提交占约 34ms；前五分钟提交均值约 31ms，后五分钟约 37ms。连接池短暂达到 100/100，累计出现 264 次连接等待。

还采到 160 条订单状态索引上的插入意向间隙锁等待，多条可识别 SQL 对应订单状态更新。数据库文件 I/O 也有数百毫秒等待，并出现内存限制回收事件，但没有 OOM。

这些是需要分别验证的候选限制：状态更新的执行计划和锁范围、数据库提交及 I/O 波动。还没有单变量对照证明唯一根因，不能直接归因于消费者数量不够，也不能认定所有阻塞都来自某一个后台任务。

## 13. 限流怎么验证？

下单入口使用独立、共用的本地令牌桶，普通下单与抢票共用 150/s、burst 50 的额度。每用户核心写接口还有 Redis 滑动窗口，全局 HTTP 和 IP 限流各自独立。

测试限流时，把其他限流层配额调高，单独看目标层。入口 150/s、burst 50，输入 500/s 持续十秒时，5,001 个请求中受理 1,545 个，3,456 个返回限流，成功受理 P99 约 66ms，k6 没有未发出的请求。

另跑放宽入口的测试，让全部高峰进入 MQ，观察排队与清空。限流拒绝和 MQ 缓冲是不同结果，分别报告。

当前入口令牌桶按实例计算；如果扩成多应用实例，总受理额度会随实例增加，需要重新规划集群额度。

## 14. 售罄、重复下单和限购怎么测试？

| 场景 | 验证结果 |
|---|---|
| 售罄 | 库存 1,000，提交 5,000 次；最终 1,000 单确认，4,000 次售罄 |
| 重复下单 | 1,000 次请求对应 100 笔逻辑订单；只生成 100 单，库存只扣 100 次 |
| 限购 | 一个用户提交 200 次不同请求，限购 20；确认 20 单，其他业务拒绝 |

检查响应分类、订单实际数量、Inbox 数量、MySQL 剩余库存及 Redis 每个桶的值。重复下单还验证相同幂等键改变请求内容会被拒绝。

售罄和限流请求可能返回得很快，所以拒绝 QPS 不能拿来当成功下单吞吐。

## 15. 故障怎么注入？能说明什么？

在独立环境停止 RabbitMQ，继续发下单请求，检查已受理订单是否持久化为 queued、Outbox 是否待发布；恢复 MQ 后等待投递和确认，并核对库存。

应用重启场景则在订单已受理、MQ 未恢复时强制终止应用，再恢复应用与 Broker，检查未完成订单能否最终确认。已测试的 MQ 中断场景最终确认 1,001 单，应用重启场景最终确认 500 单。

这验证了这些故障场景的恢复结果。没有覆盖 Redis 数据丢失、数据库主从切换、多实例网络分区，也不能宣称任何故障下都不会丢单。订单确认测试不等于支付回调、退款、关单竞争都做了同样强度的负载验证。

## 16. 混合流量怎么测？

另做了 100 个业务动作/秒、持续 60 秒的混合测试，覆盖查询、登录、注册、普通下单和抢票等动作。一个业务动作可能发多个 HTTP 请求，所以动作速率不能直接叫 HTTP QPS。

本轮共 6,481 次 HTTP 请求、1,133 笔订单，各动作业务成功率为 100%。但普通下单和登录的 P99 分别约 1.06 秒和 1.08 秒，因此正确性通过不表示所有接口延迟都达到了目标。它是短时验证，不代表混合流量的长期容量上限。

## 17. 150 单/秒是不是不够高？

这里测的是包含数据库持久化、Outbox、MQ、Consumer 和库存确认的实际订单链路。测试刻意限制资源，并且保持 redo/binlog 双 1。

我会给出链路、资源配置、延迟和确认吞吐，让面试官判断，而不是把成功订单、快速拒绝响应、缓存查询 QPS 混成一个漂亮数字。项目的价值在于解释如何定位限制、提高确认吞吐并验证一致性，而不是给单机数字贴一个绝对标签。

## 18. 接下来怎么优化？

优先对订单状态 UPDATE 的执行计划、状态索引锁范围及 Consumer 事务隔离级别做单变量验证；数据库提交/I/O 和内存回收也分开对照。

验证指标是：相同输入下确认吞吐、订单确认 P99、HTTP P99、锁等待、连接等待和最终一致性。已有证据不支持仅靠增加 Consumer 就能解决全部问题。

## 简历可以使用的表述

使用 k6 完成阶梯、持续和故障场景压测，结合 Prometheus 指标与 MySQL 行锁信息定位发布及消费瓶颈；通过 Outbox 状态合并更新、Consumer 查询精简与并发调整，将 300 请求/秒档位的确认吞吐由约 128 提升至 250 单/秒。完成 150 单/秒持续 25 分钟验证，HTTP P99 约 162ms，并验证短高峰后队列消化及订单、库存一致性。

不使用“稳定 500 QPS”“长期稳定 250 单/秒”“所有故障下零丢单”作为已验证结论。
