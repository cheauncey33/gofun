每道题按四段回答: 通用方案、项目当前方案、项目不足、生产扩展。反问用于确认面试官关注点，追问用于自测能否扛住连续深挖。

## 1. 如何防止超卖？

通用方案: Redis 原子扣减、Lua、数据库条件更新、唯一约束、MQ 削峰、补偿任务。

项目方案:

- 普通下单用 Redis Lua 对多个商品库存先检查再扣减。
- 秒杀用 Redis Lua 同时校验 token、库存、用户限购。
- MySQL 事务落库时用 `WHERE stock >= num` 条件更新兜底。
- MQ 投递失败会回滚 Redis 库存。

项目不足: 没有完整处理所有极端宕机窗口，生产可加本地消息表、死信队列和更完整补偿。

可反问:

- 面试官更关注单机 Redis 原子扣减，还是分布式异常下的一致性？
- 是讨论普通下单超卖，还是秒杀活动超卖？

连续追问:

1. 为什么 Redis Lua 能原子防超卖？
2. Redis 防了，MySQL 为什么还要条件扣减？
3. 多商品下单时如何保证要么都扣要么都不扣？
4. Lua 成功但 MQ 失败怎么办？
5. MQ 成功但 DB 失败怎么办？
6. DB 条件扣减失败后 Redis 怎么恢复？
7. 秒杀用户限购如何避免并发绕过？
8. 生产上是否需要 DB 唯一索引兜底？

## 2. 缓存一致性怎么做？

通用方案: Cache Aside、短 TTL、主动失效、延迟双删、binlog 订阅、最终一致补偿。

项目方案:

- 商品列表查询走 L1 本地缓存 -> L2 Redis -> MySQL。
- 管理端商品变更后清空本地缓存，并扫描删除 `product:list:*` Redis key。
- 商品库存变更通过 Redis 预扣和 MySQL 条件扣减配合。

项目不足: 没有 binlog 订阅和分布式缓存广播，多实例本地缓存一致性需要扩展。

可反问:

- 讨论的是商品列表缓存，还是库存缓存？这两个一致性要求不一样。
- 是单实例部署还是多实例部署？多实例下本地缓存失效要额外设计。

连续追问:

1. 商品列表更新后如何清 Redis？
2. 本地缓存如何清？
3. 多实例下本地缓存怎么同步失效？
4. 为什么不用延迟双删？
5. Redis 删除失败怎么办？
6. 缓存 TTL 固定有什么风险？
7. binlog 订阅能解决什么？
8. 库存缓存和商品详情缓存能用同一套策略吗？

## 3. 缓存穿透、击穿、雪崩怎么办？

项目当前:

- 没有布隆过滤器。
- 商品列表有短本地缓存和 Redis 缓存。
- Redis TTL 固定 5 分钟，没有随机扰动。

回答口径:

可反问:

- 面试官问的是恶意请求不存在 ID，还是热点 key 失效？
- 是读接口缓存问题，还是库存 key 问题？

连续追问:

1. 缓存穿透和击穿区别是什么？
2. 空值缓存 TTL 应该多长？
3. 布隆过滤器误判怎么办？

5. 为什么 TTL 要加随机值？
6. 本地缓存能不能解决雪崩？
7. 秒杀库存 key 能不能设置 TTL？

## 4. 热点 key 怎么处理？

- 是单商品热点还是全站热点？处理方式不同。

## 5. MQ 重复消费怎么办？

- `seckill_order.order_id` 有唯一索引。

- 建幂等表。
- 业务状态机防重复流转。

## 6. MQ 消息丢失怎么办？

项目当前:

- 队列 durable。
- 消息 `DeliveryMode: Persistent`。
- 消费端手动 ack。

不足:

- 没有 publisher confirm。
- 没有 mandatory return 处理。
- 没有死信队列。

回答:

当前实现了基础可靠性，但生产要补 publisher confirm、投递失败日志、本地消息表、死信队列和告警。

可反问:

- 面试官问的是生产者丢、Broker 丢，还是消费者处理失败丢？三段保障不同。
- 是否要求强可靠，还是允许最终一致补偿？

## 7. MQ 消息积压怎么办？

项目经验:

- 简历中压测观察到 ready backlog。
- 将 consumer 从 4 workers / prefetch 5 调到 12 workers / prefetch 10。

排查顺序:

1. 看生产速度是否突增。
2. 看 consumer 是否异常退出。
3. 看 DB 写入是否变慢。
4. 看 prefetch 和 worker 是否过低。
5. 看单条消息处理耗时。

注意: 不能无限加 worker，否则会把压力转嫁给 MySQL。

可反问:

- 积压是 ready 高，还是 unacked 高？两者定位不同。
- 业务是否允许延迟消费，还是必须实时完成？

连续追问:

1. ready 和 unacked 区别是什么？
2. worker 数调大有什么副作用？
3. prefetch 太大有什么风险？
4. 如何判断瓶颈在 consumer 还是 DB？
5. 积压时是否应该扩容 producer？
6. 如何做消费者水平扩容？
7. 业务高峰后如何自动恢复？
8. 死信消息会不会造成积压？

## 8. Redis 扣库存成功但 DB 失败怎么办？

项目方案:

- MQ 投递失败时，入口处立即回滚 Redis。
- consumer DB 失败时 nack 重试。
- 普通库存有定时补偿。

不足:

- 如果业务错误永久失败，可能一直 requeue。
- 秒杀 user_count 的补偿不完整。

生产扩展:

- 重试次数上限。
- 死信队列。
- 失败订单表。
- 人工修复后台。
- 定时核对 Redis、订单表、商品表、秒杀订单表。

可反问:

- DB 失败是临时故障，还是余额不足/商品下架这类业务失败？
- Redis 扣库存成功后，MQ 是否已经投递成功？不同阶段处理不同。

连续追问:

1. MQ 投递失败为什么可以直接回滚？
2. consumer DB 失败为什么不能直接回滚 Redis？
3. 可重试错误和不可重试错误怎么区分？
4. 余额不足导致失败时应该 requeue 吗？
5. 如果服务在回滚前宕机怎么办？
6. 补偿任务如何发现少卖？
7. 秒杀 user_count 如何补偿？
8. 如何保证补偿任务本身幂等？

- IP 限流是单机内存版。

可反问:

## 10. 用户重复下单怎么办？

扩展:

- `(user_id, idem_key)` 唯一索引。

## 11. 服务重启如何不丢消息？

项目方案:

- RabbitMQ 队列和消息持久化。
- consumer 手动 ack。
- 优雅停机时 cancel context，等待 worker 退出。
- HTTP server `Shutdown` 等待请求完成。

不足:

- 正在处理的消息如果进程被强杀，RabbitMQ 会在连接断开后重新投递未 ack 消息，依赖幂等保证不重复落库。
- 没有 publisher confirm。

可反问:

- 是正常发布重启，还是机器强杀/断电？可靠性等级不同。
- 关注 HTTP 请求不丢，还是 MQ 消息不丢？

连续追问:

1. `srv.Shutdown` 做了什么？
2. consumer 如何收到退出信号？
3. 正在处理的消息能否处理完再退出？
4. 强杀时未 ack 消息怎么办？
5. 重投后如何避免重复订单？

7. 如何配合容器的 terminationGracePeriod？

## 12. 数据库连接池被打满怎么办？

- MQ 削峰，让 DB 写入由固定 worker 消化。
- MySQL 配置 `max_open_conns`。

排查:

- 慢 SQL。
- worker 数过高。
- 事务过长。
- 索引缺失。

可反问:

- 是读连接打满还是写事务打满？
- 是连接泄漏还是下游 SQL 太慢？

连续追问:

1. 如何查看连接池状态？

## 14. 管理端更新订单状态有哪些风险？

- 管理端用 `CanTransitionTo` 限制订单状态流转。

项目不足: 管理端状态更新缺少操作审计，也存在 Redis 库存回补不完整问题。

生产扩展:

- 管理员操作日志。
- 状态变更原因。
- Redis 和 DB 同步补偿。
- 支付退款回调对接。

可反问:

## 15. 地址和订单收货信息如何设计？

项目当前:

- 地址表支持增删改查和默认地址。
- 更新、删除、设置默认都用 `user_id` 防越权。
- 订单表只有 `address_id`，当前下单没有强制地址，也没有收货信息快照。

项目不足: 生产订单应保存收货人、手机号、详细地址快照，否则用户修改/删除地址会影响历史订单展示。

生产扩展:

- 下单时强制选择地址。
- 订单表增加收货信息快照字段或订单地址快照表。
- 地址默认唯一约束。

- 是否要求历史订单不受地址修改影响？
