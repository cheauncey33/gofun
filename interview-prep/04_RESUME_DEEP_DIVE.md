## 简历项目原文

项目: 独立开发 Campus-Mall 校园电商秒杀系统。

核心技术栈: Go / Gin / GORM / MySQL / Redis / RabbitMQ / JWT。

核心描述:

1. 完成普通下单与秒杀核心链路开发，将商品及活动库存预热至 Redis；基于 Lua 脚本完成库存校验、限购判断与原子预扣减，将高并发下的超卖与重复抢购问题前置拦截。
2. 引入 RabbitMQ 异步化下单流程，请求入口在 Redis 预扣库存后投递订单消息，Consumer 异步执行订单落库、库存扣减与销量更新等事务操作，削减峰值流量对 MySQL 的直接冲击。
3. 针对重复提交及异常链路，使用雪花算法生成订单 ID，并在消费端基于订单 ID 做幂等校验；补充 MQ 投递失败回滚、消费失败 Nack 重试及库存补偿机制，保障 Redis 与 MySQL 最终一致。
4. 编写 Node.js 压测脚本验证下单链路，发现 RabbitMQ ready backlog 峰值约 2.6 万；将 Consumer 从 4 workers / prefetch 5 调整为 12 workers / prefetch 10 后，消息积压基本消除，提升订单消费吞吐。

### 30 秒版

这是一个 Go + Gin 的校园电商秒杀系统。我主要围绕高并发下单做了 Redis 库存预热和 Lua 原子预扣、RabbitMQ 异步削峰、consumer 幂等落库、失败回滚、基础库存补偿、限流和 Prometheus 监控。重点是把大量无效请求挡在 Redis 层，把重的 MySQL 写事务放到 MQ 后台消费。

### 2 分钟版

项目分为用户、商品、订单、秒杀、管理端和基础设施几个部分。用户登录后通过 JWT 鉴权，商品列表有本地缓存和 Redis 缓存。普通下单时，入口先用 Redis Lua 检查多个商品库存并预扣，再生成 Snowflake 订单 ID，把订单消息投递到 RabbitMQ。后台 consumer 使用手动 ack，事务内完成商品库存扣减、余额扣减、订单和订单项创建、销量更新。秒杀链路额外加入一次性 token、活动时间校验、用户限购计数和秒杀库存 key。异常上，MQ 投递失败会回滚 Redis，消费失败会 nack 重试，重复消费通过订单 ID 幂等处理。

### 深挖版

这个项目的设计核心是“前置拦截 + 异步削峰 + DB 兜底 + 补偿”。Redis Lua 只负责高并发入口的原子校验和预扣，不能代替数据库最终一致性，所以 consumer 落库时仍然用 `WHERE stock >= ?` 条件更新防止 DB 层超卖。RabbitMQ 负责把瞬时请求转成后台可控消费，`prefetch` 和 worker 数控制消费速率。当前项目实现了基础可靠性，但没有 publisher confirm、死信队列和完整本地消息表；面试时不能把它说成完整生产级分布式事务，只能说是一个面向实习项目的高并发链路实践。

### 30 秒版

普通下单和秒杀最终都走 MQ 异步落库，但入口校验不同。普通下单主要校验商品库存，秒杀会额外校验活动时间、活动状态、一次性 token 和用户限购。

### 2 分钟版

普通下单接口是 `POST /api/v1/orders`，请求里是商品 ID 和数量。后端合并重复商品后，用 Redis Lua 对多个商品库存一次性检查和预扣，再投递订单消息。秒杀接口是先获取 token，再执行 `POST /seckill/activities/:id/execute`，Lua 脚本会同时检查 token、库存、限购，并删除 token 保证一次性。两条链路最终都生成 `OrderMessage` 给 RabbitMQ，由 consumer 事务落库。

### 深挖版

普通下单偏电商购物车场景，核心是多商品库存一致预扣；秒杀偏高并发抢购场景，核心是活动维度库存、用户限购和防刷。HTTP 返回成功只说明请求通过入口拦截并进入异步处理，不等同于订单已经落库。生产上应补订单状态查询、前端轮询或 WebSocket 推送；当前项目还没有实现这部分，所以面试回答要说清楚这是异步链路的交互待完善点。

### 30 秒版

预热是为了让下单入口先访问 Redis，而不是让所有并发请求直接打 MySQL。普通商品启动时写 `snack:stock:{productID}`，秒杀活动由管理端预热写 `seckill:stock:{activityID}`。

### 2 分钟版

普通商品库存预热在服务启动阶段执行，遍历商品表，把库存写入 Redis。秒杀活动库存预热通过管理端接口触发，会校验活动时间，然后写活动库存并更新活动状态。这样秒杀或下单时入口可以在 Redis 内完成快速校验和预扣，MySQL 只处理已经通过初筛的请求。

### 深挖版

Redis 库存是高并发入口的“快速状态”，MySQL 仍然是最终落库事实。普通商品补偿任务会扫描商品表，发现 Redis 库存 key 缺失就按 DB 重建，发现 Redis 库存大于 DB 库存就修正。秒杀活动库存补偿当前还不完整，生产应结合活动表、秒杀订单表和用户购买计数一起核对。多实例启动重复写普通库存可能覆盖运行中库存，所以生产环境应把预热和运行态扣减做更严格的启动编排或版本保护。

### 30 秒版

Lua 是为了把多个 Redis 操作合成一个原子操作。普通下单先检查所有商品库存再统一扣减；秒杀额外检查 token 和用户限购，成功后删除 token、扣库存、增加用户购买计数。

### 2 分钟版

如果用 `GET` 再 `DECR`，中间可能被其他请求插入，导致判断和扣减不一致。Lua 在 Redis 内作为一个整体执行，可以把检查库存、检查限购、扣库存放在同一个原子脚本中。普通下单的脚本支持多商品，任一商品不足就不扣任何商品。秒杀脚本会读取 `seckill:token`、`seckill:stock` 和 `seckill:user_count`，分别处理 token、库存和限购。

### 深挖版

Redis 单线程保证单条命令原子，但不能保证多条命令之间不被插入，所以需要 Lua 把多命令合并。Lua 不能写太重，否则会阻塞 Redis 主线程。项目里 Lua 只做 O(n) 的库存 key 检查和扣减，逻辑较短。即使 Redis Lua 成功，MySQL 落库仍可能失败，因此 consumer 在 DB 层仍用条件更新兜底。生产上还会加入限流、降级和 Redis 故障策略，比如活动临时关闭或转入排队页。

### 30 秒版

项目把大部分超卖和重复抢购拦在 Redis 层。秒杀 Lua 会校验库存、用户购买数量和一次性 token，DB 层再用条件扣库存兜底。

### 2 分钟版

超卖是卖出的数量超过真实库存。项目在入口用 Redis Lua 做原子预扣，库存不足直接失败，不进入 MQ。重复抢购主要通过秒杀用户计数和一次性 token 控制，一个 token 用完就删除，用户购买数量超过 `limit_per_user` 就失败。落库时 MySQL 仍检查商品库存 `stock >= num`，防止 Redis 异常或补偿窗口带来的风险。

### 深挖版

这里的“前置拦截”不是说系统绝对不会出现任何一致性问题，而是说把高并发失败请求尽量挡在 Redis 内存层。普通下单的重复点击没有完整请求幂等 key，只能靠每次生成不同订单处理，所以这是不足。生产可加 `(user_id, idempotency_key)` 唯一约束、前端防重复提交、秒杀活动 `(user_id, activity_id)` 唯一索引以及更完整的补偿核对。

### 30 秒版

MQ 用来削峰和异步化。入口只做 Redis 预扣和消息投递，把重的 MySQL 事务交给后台 consumer，避免瞬时流量直接打满数据库连接池。

### 2 分钟版

订单消息包含订单 ID、用户 ID、秒杀活动 ID、秒杀价和商品列表。队列是 `order_queue`，队列 durable，消息 Persistent。consumer 关闭 auto ack，处理成功才 ack，处理失败 nack 重新入队。这样可以把入口请求耗时从“Redis + DB 事务”降到“Redis + MQ publish”，并让 DB 写入由固定数量 worker 消化。

### 深挖版

RabbitMQ 更适合传统业务队列、路由和确认机制，项目里只需要订单异步处理，不需要 Kafka 的超高吞吐日志流模型。当前可靠性是基础版: durable queue + persistent message + manual ack，但没有 publisher confirm、mandatory return、死信队列、重试上限和本地消息表。所以面试时要说“实现了基础可靠性和幂等，生产还要补完整消息可靠性闭环”。

### 30 秒版

consumer 事务里会查商品、条件扣库存、扣用户余额、创建订单、创建订单项、更新销量，秒杀场景还会写秒杀订单表。任一步失败，MySQL 事务回滚。

### 2 分钟版

`ProcessOrderTask` 先做订单 ID 幂等检查，然后进入 GORM Transaction。它批量查商品，校验商品存在且在售；对每个商品执行 `stock >= num` 的条件更新；按商品价或秒杀价计算总金额；扣用户余额；创建订单和订单项；增加商品销量；如果是秒杀订单，再写 `seckill_order`。这些操作放在一个事务里，是为了保证 DB 内部状态一致。

### 深挖版

事务越长并发压力越大，所以入口用 Redis 和 MQ 限制进入 DB 的请求量。DB 层的条件扣库存是最后兜底，不是主要抗流量手段。当前事务失败后 consumer nack 重新入队，但如果是余额不足或商品下架这种业务永久失败，反复重试不理想。生产应区分可重试错误和不可重试错误，不可重试进入失败表或死信队列，并执行 Redis 预扣补偿。

### 30 秒版

异步下单时订单还没入库，但消息和幂等都需要一个稳定订单 ID，所以用 Snowflake 在应用层生成。consumer 处理前按订单 ID 查重，已存在就直接 ack。

### 2 分钟版

Snowflake 通常由时间戳、机器 ID 和序列号组成，能生成趋势递增的分布式 ID。项目里下单入口生成订单 ID 后放进 MQ 消息。consumer 收到消息后先查 `order` 表是否已有这个 ID，如果有说明是重复消费，直接返回成功；如果没有再执行事务创建订单。

### 深挖版

查询再插入理论上有并发竞态，所以生产上必须依赖数据库唯一约束兜底。项目的订单 ID 是主键，插入重复主键会失败；更严格做法是捕获 duplicate key 并视为幂等成功。Snowflake 的风险是时钟回拨和机器 ID 冲突，生产要通过 NTP、发号器保护、节点 ID 编排和回拨等待/拒绝策略处理。

### 30 秒版

MQ 投递失败时，普通订单回滚 `snack:stock`，秒杀订单回滚 `seckill:stock` 和 `seckill:user_count`。consumer 失败时 nack 重新入队，另有普通库存补偿任务定期修正 Redis 和 DB 的部分不一致。

### 2 分钟版

入口 Redis 预扣成功后，如果 RabbitMQ 发布失败，说明订单没有进入异步处理，所以要立即把 Redis 库存加回。秒杀还要把用户购买计数减回。consumer 处理失败时用 `Nack(false, true)` 让消息重新入队，适合数据库短暂抖动这类可恢复错误。补偿任务每 5 分钟扫描普通商品库存，Redis key 缺失就重建，Redis 库存大于 DB 就按 DB 修正。

### 深挖版

当前项目的最终一致是基础版本，不是完整闭环。`requeue=true` 对永久业务错误会造成反复重试；补偿任务没有覆盖所有秒杀状态；也没有死信队列、本地消息表和告警。生产级方案应将消息状态落本地表，发布成功后更新状态；consumer 区分可重试和不可重试错误；超过次数进入死信队列；补偿任务核对订单表、订单项、商品库存、秒杀活动、秒杀订单和 Redis key。

## 句 9: “保障 Redis 与 MySQL 最终一致”

### 30 秒版

这里更准确的说法是“实现了基础回滚和补偿，降低 Redis 与 MySQL 不一致窗口”。当前不是完整强一致，也不是生产级分布式事务。

### 2 分钟版

入口扣 Redis、后台写 MySQL，中间天然有短暂不一致。项目通过 MQ 投递失败立即回滚、consumer 失败重试、普通库存定时补偿来尽量收敛不一致。MySQL 仍是最终事实，Redis 是入口快速状态。

### 深挖版

如果面试官深追，我会主动说明当前方案不足: 缺少完整死信处理、缺少本地消息表、缺少秒杀维度完整补偿。生产要做到可靠最终一致，需要把每个状态变化可观测、可重试、可补偿，包括消息状态、订单状态、库存差异和人工介入入口。

## 句 10: “Node.js 压测脚本、RabbitMQ ready backlog、worker/prefetch 调优”

### 可能追问

1. 压测脚本怎么写的？
2. 你压的是哪个接口？

4. unacked 又是什么？

6. prefetch 影响什么？

8. 调大一定更好吗？
9. 还应该看哪些指标？

11. DB 连接池配置是多少？
12. 如果 backlog 继续增长怎么办？

### 30 秒版

ready backlog 表示队列中等待消费的消息数量。worker 提高并发消费能力，prefetch 控制每个 worker 最多持有多少未 ack 消息。调大后 backlog 明显下降，但也要同时看 DB 压力和错误率。

### 2 分钟版

项目用 Node.js 脚本模拟下单流量，观察 RabbitMQ 管理端的 ready backlog。初始 consumer 并发较低时，生产速度超过消费速度，队列堆积明显。后来把 worker 数从 4 调到 12，把 prefetch 从 5 调到 10，相当于提高消费并发和单 worker 拉取窗口，使 MQ 积压下降。

### 深挖版

这类调优不能只看 backlog。worker 太多会增加 MySQL 并发事务和连接池压力，prefetch 太大可能导致某些 worker 持有过多消息，失败时重投延迟增加。完整压测还应看 QPS、成功率、平均 RT、TP95/TP99、DB 慢 SQL、连接池、Redis 延迟、RabbitMQ ready/unacked、consumer 单条耗时和机器资源。当前项目已有压测实践，但还需要形成更完整的压测报告。
