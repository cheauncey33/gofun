```
Redis 快主要有几个原因。
第一，它是内存数据库，大部分读写都在内存中完成，避免了磁盘随机 I/O。
第二，Redis 的命令执行主流程是单线程的，避免了多线程锁竞争和频繁上下文切换，而且单条命令执行时间通常很短。
第三，它采用 I/O 多路复用，一个线程可以同时监听大量客户端连接，连接有读写事件时再处理，所以网络模型比较高效。
第四，Redis 的底层数据结构做了很多优化，比如 String 使用 SDS，List 使用 quicklist，Hash/Set/ZSet 会根据数据规模在紧凑结构和哈希表、跳表之间切换，既节省内存又保证常见操作性能。
```
```
Redis的数据结构底层原理是什么？
Redis 顶层 key 空间是 dict，也就是哈希表。不同 value 类型有不同底层编码。String 是 SDS；List 现在主要是 quicklist；Hash 小数据量用 listpack，大了转 hashtable；Set 小整数集合用 intset，大了转 hashtable；ZSet 小数据量用 listpack，大了用 skiplist 加 dict。这样做的核心是根据数据规模在节省内存和查询效率之间做平衡。
```
```
Redis都是单线程吗？哪些是多线程？
严格说 Redis 不是所有东西都是单线程。我们通常说的单线程，指的是核心命令执行流程主要由主线程串行处理。后台持久化、异步删除、AOF 刷盘、Redis 6.0 后的网络 I/O 读写（在6.0之前是和命令共同作为主线程的），都可能用到其他线程或子进程。但命令执行本身串行，保证了很多操作天然原子，也避免了复杂锁竞争。
```
```
I/O多路复用是什么？
I/O 多路复用就是用一个线程（redis的I/O线程不是命令线程，网络I/O线程是多线程的）同时监听多个网络连接（客户端和redis建立的，是tcp连接，在redis初始化时设置了PoolSize=50 相当于连接池上限为50）。比如 Linux 下常见是 epoll，Redis 把客户端 socket 注册到事件循环里，当某个连接可读或可写时，事件循环才回调处理。这样不需要为每个连接创建一个线程，减少线程切换和内存开销，所以可以支撑大量连接（tcp）。

I/O复用的具体模型是什么？
Redis 底层会根据操作系统选择不同的 I/O 多路复用机制。在 Linux 上主要使用 epoll，在一些其他系统上可能使用 kqueue、select 等。
select 的特点是每次需要扫描一批文件描述符，连接多了以后开销会比较大，而且有连接数限制。epoll 更适合大量连接场景，它把要监听的 socket 注册到内核，事件就绪时内核通知应用程序，不需要每次遍历所有连接，所以在高并发连接下效率更高。

tcp连接动态扩张策略是什么？（是客户端管理的、go-redis）
是否有空闲可以用？没有空闲是否还能扩张？不能扩张只能等待空闲

I/O多路复用：
综合回答：Redis 基于事件循环处理网络请求。它不会一个客户端连接开一个线程，而是把多个 socket 注册到 I/O 多路复用器里。哪个 socket 有可读或可写事件，就被事件循环取出来处理。Linux 下 Redis 通常使用 epoll；其他系统可能使用 kqueue 或 select。
select 的问题是连接多时需要遍历大量 fd，开销比较高；epoll 是把 fd 注册到内核，等事件就绪后由内核通知应用，所以更适合大量连接但不是每个连接都一直活跃的场景。
放到我的项目里，秒杀时多个 Go 后端连接会同时向 Redis 发 Lua 请求，Redis 可以用 epoll 同时监听这些连接，发现哪个连接有请求就读取命令，然后交给主线程串行执行 Lua。这样网络连接管理是高效的，同时命令串行执行又保证了库存扣减这类操作的原子性。
```

```
Redisson是啥？
Redisson 是 Java 生态里一个比较常用的 Redis 客户端，它不只是简单封装 GET/SET，还基于 Redis 封装了很多分布式对象和工具，比如分布式锁、可重入锁、读写锁、延迟队列、限流器、布隆过滤器等。我项目是 Go 写的，没有直接用 Redisson，但类似分布式锁能力可以用 Redis 的 SET key value NX EX 加 Lua 解锁来实现。
Go 生态里有 redsync、redislock 这类 Redis 分布式锁库，但不像 Java 的 Redisson 那样提供完整分布式对象封装。我项目里没有用可重入锁，而是用 SET NX EX + UUID value + Lua 解锁 实现普通排他分布式锁。因为下单场景只需要限制同一用户同一时间只能进入一次下单流程，没有同一线程或同一请求重复进入同一把锁的需求，所以不可重入锁更简单，也更容易验证正确性。

Redis Cluster上的热点key怎么处理？
这个我项目里没有实际做 Redis Cluster 热点治理，但我理解热点 key 主要分读热点和写热点。读热点可以通过本地缓存、多级缓存、热点 key 副本、读写分离来缓解；写热点比较难，因为同一个 key 的写必须保证一致性，通常要做限流、削峰、拆 key 或者业务上降低单 key 写频率。我的项目里更接近的是用本地缓存和 IP 限流降低对 Redis 的压力，但没有做到完整 Cluster 热点治理。

关于微服务：
这块我没有实践过，所以不展开乱讲。我目前项目是单体加中间件部署，主要关注 Redis、MQ、MySQL 的链路可靠性。如果做多实例服务发现，我理解至少需要注册中心、健康检查、负载均衡和故障摘除，具体 Consul/Eureka 的实现细节我还需要补。
```

2、为什么用rabbitmq？不是还有各种kafka、RocketMQ吗？ 面试时不要答rabbitmq好因为他不好，而是结合业务场景去回答。你的mq用到了什么兜底策略，比如持久性怎么保证的（只有一个持久化参数设置？）？、

```
我项目里用 RabbitMQ，主要是为了做下单链路的异步削峰。普通下单和秒杀下单入口先在 Redis 里用 Lua 做库存校验和预扣，成功后把订单消息投递到 RabbitMQ，再由后台 consumer 按固定 worker 数和 prefetch 去做 MySQL 事务落库。这样可以避免秒杀瞬时流量直接打到 MySQL，也能让数据库写入压力变得可控。
选 RabbitMQ 是结合项目场景考虑的。我的场景是典型的业务队列：订单异步处理、手动 ack、失败重试、控制消费速度。RabbitMQ 的队列模型、ack 机制、prefetch、死信队列和 publisher confirm 都比较直接适配。
Kafka 更适合高吞吐日志流、埋点、数据管道、可回放消费这类场景，它的核心是 topic-partition 的日志模型。我的项目不是日志采集，也不需要特别大的流式吞吐，所以 Kafka 不是最优先。
RocketMQ 也很适合电商业务消息，支持事务消息、顺序消息、延迟消息等，但部署和使用复杂度相对更高。作为个人项目，我更需要一个轻量、容易落地、能覆盖订单异步削峰的 MQ，所以选择 RabbitMQ。
可靠性上，我做了几层兜底。第一，队列声明为 durable，消息设置 DeliveryMode = Persistent，保证 broker 重启后消息更不容易丢。第二，发布端开启 publisher confirm，生产者发完消息后等待 RabbitMQ broker 确认；如果确认失败或超时，就认为订单排队失败，并回滚 Redis 预扣库存。第三，consumer 关闭 auto ack，只有 MySQL 事务处理成功后才手动 ack；如果处理失败，会记录重试次数，未超过上限就进入重试队列，超过上限就进入死信队列。第四，因为 RabbitMQ 是至少一次投递语义，可能重复消费，所以 consumer 会用订单 ID 做幂等校验，订单 ID 也是数据库主键，重复消息不会重复落库。
所以我现在不是只设置了一个持久化参数，而是做了 durable queue、persistent message、publisher confirm、manual ack、重试/死信队列、Redis 回滚和订单 ID 幂等。不过这仍然不是完整分布式事务，生产上还可以继续补本地消息表、失败消息管理后台和告警。

消费者和broker的关系：
每个消费者通过consume在broker注册身份 msgs, err := ch.Consume(...) 其中msgs是<-chan amqp.Delivery 类型
broker按照prefetch数目给消费者push消息到msgs中，consumer是select监听msgs的
```

```
可以总结为三个条件，必须同时满足才会触发消费者超时：
连接正常：TCP 连接没有断开，心跳也正常。
存在未确认消息：该消费者（Channel）上，至少有一条消息处于 unacked 状态。
```

```
在重复投递了不可重试错误的情况下会回滚。

那什么情况下发生重复投递？组件异常，网络波动可以恢复。
因为RabbitMQ 是至少一次投递，应该先了解RabbitMQ到底什么时候会重新投递消息：
1、首先这条消息已经被投递出去但是没有ack，处于unacked状态。
2、以下都会让mq重新投递发出去但是unacked的消息：consumer异常，amqp channel异常。注意网络波动导致的ack丢失rabbitmq是不会重投的，因为mq的语义是at-least-once delivery：至少投递一次，不保证只投递一次。况且RabbitMQ consumer 和 broker 通信通常用的是 AMQP 协议，跑在 TCP 长连接 上，严格意义上的“ack 悄悄丢失但双方都完全正常”基本不会长期成立。因为TCP本身会做：可靠传输|顺序保证|丢包重传|连接异常检测。注意TCP连接是有序的是指字节顺序有序，但是多条消息传递过去，那么多消费者，消费者自己又有preftech，谁先执行完，就不一定了，所以TCP的顺序保证不是RabbitMQ的顺序保证。
```

4、SSO、JWT的优缺点？为什么使用JWT？不用redis+token？有cookie、session为啥用JWT？SSO可以结合校园的统一认证回答。

```
首先明确概念：
Cookie是浏览器保存数据的机制，不是认证方案本身，假如使用Session，那么session_id就可以存放在Cookie中，Cookie还可以放其他数据比如：用户语言偏好=zh-cn、主题设置=dark、购物车ID=xxx。
Session 是服务端保存登录态，浏览器通常只用存一个session_id在Cookie中。
Token 是一种登录凭证，可以放在 Header 或 Cookie 里。
JWT 是一种自包含 Token，里面可以带 user_id、过期时间、签名等信息。
（Token和JWT的区别就是Token是饮料，那JWT就是可乐）

为什么选用JWT？
我这个项目是前后端分离的校园电商系统，后端主要提供 REST API，所以认证上选择 JWT。用户登录后，后端签发 access token 和 refresh token。平时访问商品、订单、下单、秒杀、管理端接口时，前端只把 access token 放到请求头，后端中间件验签后解析出 user_id，不需要每次都查 Redis 或维护传统 Session，认证链路比较轻，也方便后续水平扩展。
但我没有把 JWT 做成一个长期 token，因为长期 access token 泄露后风险窗口太大。所以项目里采用双 token：access token 有效期短，只负责访问业务接口；refresh token 有效期长，只负责在 access token 过期后换新 token。refresh token 同时会存 Redis，退出登录、改密码或刷新时可以删除旧 refresh token，让它不能继续续期。
这样做的取舍是：业务接口大部分时间仍然是无状态 JWT 校验，不会每次请求都查 Redis；只有刷新 token、退出登录这类认证生命周期操作才访问 Redis。它比传统 Session 更轻，也比单个长期 JWT 更安全。针对JWT无状态服务端无法主动失效、进行权限变更等缺点，可以在JWT 基础上引入 Redis 黑名单或 token_version，而不是一开始就把所有登录态都放 Redis。

为啥不适用redis+token或者sessionID？
Redis + token 和 SessionID 都属于服务端状态方案，可控性强，但每次鉴权都需要查 Redis 或维护 Session 状态。我的项目里 Redis 已经在库存预扣、秒杀和商品缓存里承担高并发压力，所以普通业务接口鉴权不希望再强依赖 Redis。JWT access token 可以让大部分请求只做本地验签，减少 Redis 访问和服务端状态维护；再配合 Redis 中的 refresh token 做续期和退出失效，兼顾性能和可控性。

SSO是什么？SSO（Single Sign-On，单点登录）是一种身份认证方案，允许用户只需登录一次即可访问多个相互信任的应用系统。
```

5、怎么做的压测？
```
我的压测是用 Node.js 写的轻量级脚本完成的，没有上 k6/JMeter。主要原因是项目规模不大，我更关注核心链路稳定性和瓶颈定位，所以用 Node 内置 fetch 配合 Promise.all 模拟并发 worker，通过环境变量控制并发数、持续时间和 think time。
```

8、你说你做了幂等校验，是干嘛的？为啥要做幂等校验？

```
幂等校验就是：同一个业务请求执行一次和执行多次，最终结果一样。
我项目里的幂等主要做在下单和 MQ 消费两个阶段。因为下单接口会先在 Redis 里预扣库存，然后把订单消息投递到 RabbitMQ，最后由消费者异步落库。这个链路里如果用户重复提交、MQ 重复投递、消费者重试，都可能导致重复扣库存、重复创建订单或者库存和订单不一致，所以我做了入口防重、消费端查重、数据库条件扣减和失败补偿。
在下单阶段，做了包括：下单后按钮置灰、下单请求在前端js代码生成idempotencyKey，用于防止网络波动重复提交订单。Redis Lua脚本会IdempotencyKey（也是Set NX虽然属于分布式锁类型但是一般不叫锁，单叫幂等key，因为幂等key是ttl到期后释放，不会lua主动释放，不存在竞争）+lock（下单锁，每个userID顶多一把，用完要释放）+库存/限购校验，校验成功则生成业务ID，发布消息，等待消费者校验业务ID，开启消费事务。
在消费阶段，订单以业务ID作为主键，消费者先用SQL语句查询DB确认订单不存在后，开启事务，进行库存、余额的校验。对于校验通过的事务，业务ID作为订单表主键，可以从DB层面兜底幂等性，不论消费者是否异常，DB主键的唯一性可以防止MQ重复投递后不会被消费者重复消费。对于不可重试错误，比如库存、余额不足，则在完成redis库存回滚的同时设置roll_back:业务ID的回滚幂等key（同样是分布式锁，但是不称为锁，因为不主动释放而是ttl到期后释放），防止回滚后，消费者异常，没来得及nack，mq重复投递，再次回滚库存。


为啥要做幂等，因为在分布式系统中很常见：
用户重复点击
接口超时重试 网络波动
MQ重复投递 因为RabbitMQ的语义是至少投递一次，不等于至少消费一次，为啥？因为每条消息RabbiitMQ投递后不设置超时，在消费者a连接断开后才会将发给消费者a的、处于nack的消息重新投递给消费者bcd。
消费者处理失败后重试 可能是数据库连接超时、连接池枯竭、db宕机等等 现在有做兜底吗？
Redis 扣了但 MQ/DB 没成功导致库存不一致

所以做幂等校验的目的是不是为了防止重复，而是重复发生时的处理。
```
8、超卖、少卖？
```
超卖：超卖的主要是指库存只有 1 件，但是并发来了 2 个请求，两个都扣成功了。
我们是 Redis 层先用 Lua 原子预扣，挡住高并发入口的超卖；MySQL 层再用 stock >= num 的条件更新做最终兜底,防止缓存和数据库不一致时把库存扣成负数；此外还做了redis库存单向定时补偿，若Redis > MySQL库存，则Redis 库存虚高，有超卖风险，定时任务检查后进行修改。
导致Redis库存>MySQL的情形：管理员修改库存/回滚操作幂等失效/Redis数据被误操作，脏写。

少卖：Redis 库存已经扣了，但订单没有最终成功，导致库存被占住，明明还能卖却卖不出去。
少卖主要靠回滚机制解决。因为我的下单是 Redis 先预扣、MQ 异步落库，所以只要后续 MQ 投递失败或者消费端发现订单不能成立，就必须把 Redis 预扣库存回补。为了防止重复回补导致超卖，我用 order:stock_rollback:{orderID} 做补偿幂等。最后还有定时任务做 Redis 和 MySQL 库存对账，修复异常库存缓存。
```

9、mq具体怎么用？你设置了哪些参数、哪些模式？（只有手动ack、和wokerNum/prefetch？）

```
1、publisher confirm：amqp消息发布后，等待mqBroker ack，ttl为5s，超时则redis回滚。
2、手动ack：取消auto ack。自己在消费者中处理ack，实现不可重试错误回滚和可重试错误的处理的工作。

3、durable:包括exchange/queue都做了持久化。exchange不存消息为啥要做持久化？因为要记录queue的绑定信息，各种配置等等。有个误区，那就是其实每个go-worker消费者没有队列，那prefetch是怎么实现的？所谓的exchange绑定的队列是指broker拥有的队列，比如项目中的oreder_queue，broker会通过给每条消息设置状态/消费者id来将他分配给消费者。woker通过select监听绑定的消息队列：

    select {
    case <-ctx.Done():
        return nil
    case d, ok := <-msgs:          // 监听主队列
        if !ok { return ... }
        s.handleDelivery(...)
    case d, ok := <-retryMsgs:    // 监听重试队列
        if !ok { return ... }

    }

worker-A 处理失败

broker: order_queue.retry 有新消息

ch.Qos(prefetchCount, 0, false)   // 设置一次
```

11、什么是websocket？http不同版本特性。

```
HTTP是单向的:客户端发送请求，服务端回应，连接中断（是指应用层的http协议中断，http传输层是基于tcp的，tcp连接在http1.0也是同时断开的，但是 HTTP/1.1 默认开启 keep-alive，TCP 连接会复用）。但是主要还是因为HTTP是单向的！
所以也就有了双向的WebSocket：在 HTTP 握手后升级成全双工长连接，服务端可以主动推消息给客户端。
```

不同版本的HTTP的特性：主要是解决并发性从 一次性tcp升级到tcp复用但是不能并发再升级到多路复用再直接不用tcp转为udp。

```
HTTP/1.0   每次请求新建 TCP，用完就断
              ↓ 解决：TCP 复用
HTTP/1.1   keep-alive，TCP 复用
           但同一条连接同一时间只能处理一个请求（队头阻塞）【主要是因为http请求没有id，所以虽然多个请求但是只能顺序处理，这是http层的队头阻塞】
              ↓ 解决：并发
HTTP/2     多路复用，同一条 TCP 上多个请求并发，不互相阻塞【加入了id，排队的多个请求都可以发出去，只要拥塞窗口支持，队头阻塞仍然存在（tcp层的队头阻塞），因为TCP是字节流，数据被分片处理，还有tcp的拥塞、可信传输等等导致tcp层的队头阻塞】
           还加了头部压缩、Server Push*
              ↓ 解决：TCP 本身的队头阻塞
HTTP/3     底层换成 UDP+QUIC，解决 TCP 层的队头阻塞
```

```
TCP一共两个窗口：发送方的拥塞窗口(cwnd)和接收方的接收窗口(rwnd)。
拥塞控制包括四个阶段：
1、慢启动 cwnd<ssthresh时cwnd一直按照指数增长。  
2、拥塞避免 cwnd达到ssthresh后，收到所有ack后cwnd固定增加1。 
3、快重传 收到3个重复ack 即可重传丢失的包 
4、快恢复 快重传后ssthresh、cwnd降为ssthresh一半 开始拥塞避免；如果时ack超时直接cwnd=1，ssthresh降为一半
```

你系统中的订单状态查询是怎么做的？

```
系统中根本没有做订单状态查询！
“下单成功”的http请求只要返回200也即：请求幂等通过、redis加锁、库存校验扣减通过，消息入队成功，此时broker收到消息返回200状态码，前端提示“下单成功”。
但是用户看到下单成功，但此时订单可能：
-还在 MQ 队列里排队
-consumer 还没处理完
-极端情况 consumer 处理失败了

但是对于支付、确认收货、取消订单的操作都是同步的。为啥？因为是否需要异步，看的是流量形态：
```

|              | 下单（秒杀/抢购）          | 支付/取消/确认                       |
| :----------- | :------------------------- | :----------------------------------- |
| 流量形态     | **瞬时尖峰**，同一秒万人抢 | **时间打散**，15分钟付款窗口内陆续点 |
| 竞争热点     | 同一个商品库存行，万人争抢 | 各人付各人的单，行级无竞争           |
| 是否需要削峰 | 需要（Redis预扣+MQ）       | 一般不需要                           |

```
下单的痛点是同一行库存的写竞争 + 瞬时尖峰，所以用 Redis Lua 把竞争挡在内存层、用 MQ 把尖峰削平。
支付是每个用户改自己的订单行、扣自己的余额——行与行之间没竞争，流量又是天然打散的。而且支付用户就是想立刻知道"钱扣没扣成功"，同步返回反而是更好的体验。所以一般不改。
高并发改造不是"全异步"，而是先定位瓶颈再选工具：读热点用多级缓存，瞬时写尖峰+行竞争用 Redis 预扣+MQ 削峰，整体 TPS 高用水平扩容+分库分表+读写分离，超级热点行用拆分。
我的下单走异步是因为秒杀的"瞬时尖峰+同一库存行竞争"；支付是每人改自己的单、流量天然打散、且用户要即时结果，所以保持同步。只有接入第三方支付网关这种有外部延迟的场景，支付才需要异步+回调+消息推送。
```

11、缓存击穿、穿透、雪崩怎么应对？（其实概念都没记清、、还有布隆过滤器怎么用的原理是什么？）

```，
穿透：查不存在的key，每次都会打到db
击穿：某个热点key失效，同时此时超高流量连接使用该key，但因为过期，全都打到db
雪崩：大量key同时过期/或者redis宕机
```
```
对于穿透：
1、参数校验：在访问redis之前校验，比如id<=0直接http请求返回400
2、缓存空值：使用cache-aside机制，查不到缓存也对该key存一个值null，设置短ttl。
3、布隆过滤器：在访问redis前，通过过滤器校验“这个key可能存在吗”（不存在一定过滤，但是可能存在的key也被过滤）
```
```
布隆过滤器原理：
查询 "product:9999"：
  hash1=3 → 第3位是1 ✓
  hash2=7 → 第7位是1 ✓
  hash3=20 → 第20位是0 ✗   ← 只要有一位是0，一定不存在！
  → 直接返回"不存在"，不查 Redis/DB
```
```
对于击穿：
1、互斥锁：只允许一个http请求携程查询db重建缓存。 
2、热点key永不过期+后台定时刷新
3、不设置过期时间，使用逻辑过期：使用hash或者json序列化当作值的string类型 value字段同时存data和expiretime
怎么判断热点key：
1、业务预判，需要配合运营。
2、redis自带的工具，比如redis-cli --hotkeys
3、监控统计incr/decy的计数

```
```
对于雪崩：
存在两种雪崩情况：一是一批缓存使用相同的ttl/二是redis整个宕机
1、ttl加随机值
2、多级缓存比如前置的L1的go-cache
3、限流+熔断降级：redis挂掉时限制打到db的流量
4、redis高可用：使用主从+哨兵/集群。
```

12、死信队列有了解吗？

```
什么是死信队列
"死信"（Dead Letter）就是没法正常消费的消息。这些消息被路由到一个专门的队列（DLQ），方便人工排查和补偿，而不是直接丢弃。
哪些消息会被送入死信队列：
1、消费者主动reject/Nack 并且requeue=false
2、消息在队列中处于ready但是超过ttl（message-ttl队列级别ttl，整个队列所有消息统一ttl）或者超过消息级别的ttl（amqp发布时可以指定expiration字段）
3、队列满了
但是我们的项目是没有设置2/3情况下的自动投递到死信队列中的。项目中是对不可重试错误手动publish到dlx（交换机）中，再由dlx路由到dlq中。
这样做的好处：retry 次数完全由业务层控制，且每次重试都可以加延迟（加 TTL 就行），逻辑清晰可观测。

死信队列的处理一般是兜底警告+人工排查
```



13、你刚刚提到主从、集群，这些具体概念是什么？你是怎么保证主从redis服务器之间数据的一致性的？redis集群三大方案（主从/哨兵/集群）怎么选？用了集群后业务有什么变化？代码需要做什么处理？ 什么脑裂/raft/选举都是什么？ 主从复制方案下，怎么保证主redis读写时，系统仍能拿到真实数据？

```
主从复制（master/slave）:只写master，写完master异步复制到slave中。
Master 处理所有写，Slave 只读（分担读压力）
复制默认异步：Master 写完立刻返回，再后台同步给 Slave
Master 挂了？手动切换，没有自动故障转移

哨兵模式（sentinel）：在主从复制的基础上加上自动转移。
奇数个哨兵同时监听同一个master，同时哨兵之间进行互相通信。
为什么是多哨兵？为什么是奇数个？
多哨兵是为了避免某个哨兵波动认为master宕机，哨兵之间的通信可以避免。
奇数个是因为更经济，更省钱。

集群模式（cluster）：在主从+哨兵的基础上进行分片。
按照key的crc16 hash分散到16384个slot中，每个节点负责一段。
同时解决了高可用（宕机处理、自带故障转移）+水平扩容



主从方案怎么保证读到真是数据？也就是一致性问题：
1、强制读master，slave单纯只做备份。
2、写后读同一个节点：下单后的查询，同意请求上下文内强制走master
3、使用等待复制确认wait命令：
SET key value
wait 1 100 #等至少1个Slave同步完，最多等100ms

写完后调 WAIT，确认 Slave 收到再返回。强一致但牺牲延迟。
4、接受最终一致性
业务上容忍短暂延迟，比如库存扣减走master，展示页读slave旧数据也可以 等待异步复制，保证最终一致性即可。
```

```
   └─ 【注意】不校验余额，不扣余额！← 代码第365行注释写明了

   WS 推送"订单已创建，请尽快支付"

        ↓ 用户看到订单，点击"支付"按钮

③ PayOrder（同步，MySQL事务）
   ├─ 条件更新：WHERE id=? AND status=Pending → status=Paid
   │   RowsAffected=0 → 拒绝（已被超时取消或重复支付）
   └─ 扣余额：WHERE id=user AND balance >= totalPrice

        ↓ 若15分钟内没支付

④ order_delay_queue TTL到期 → 消息变死信 → order_timeout_queue
   processTimeout（MySQL事务）
   ├─ WHERE id=? AND status=Pending → status=Cancelled
   ├─ 回补 MySQL 库存

   └─ 【注意】不退余额！← 因为Pending状态从未扣过钱
```
