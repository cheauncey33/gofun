***关于JWT：***
当前项目是单 JWT。登录成功后后端生成 JWT 返回给前端，前端存在浏览器 localStorage 的 token 字段里。之后 axios 请求拦截器每次从 localStorage 取 token，放到 HTTP 请求头 Authorization 里。后端中间件每次收到请求后解析这个 header 里的 JWT，验签成功后把里面的 user_id 写入本次请求的 Gin Context，供后续 controller/service 使用。

***关于Gin***——我理解的是：用户登录以后，后面的每个请求都共用同一个Gin Context
实际上：每个RestFul请求都有一个独立的gin.Context

CodeX：Gin Context 是请求级上下文，不是会话，Gin Context 在**服务端内存里**，而且只活在**当前这一次请求生命周期内**。它只在服务端处理当前 HTTP 请求时存在。登录之后服务端不会为这个用户长期维护一个 Context，前端每次请求都带 JWT，后端每次解析 JWT，再把 user_id 写入本次请求的 Context，方便后续业务代码获取当前用户身份。Context 是后端框架为每个请求创建的临时对象，后端中间件解析 token 后把 user_id 写进去，方便后续处理函数不用反复解析 JWT。前端的localStorage里面存了一个字段名对应token的字符串，之后的每次请求都会带上他。

***关于Authorization：***
这个是前端http请求中的关键字 目前项目就是如果localStorage中token字段存在 就会带上Authorization，并且赋值为localStorage的“token”：

```js
//这是js代码
const token = localStorage.getItem('token')
if (token) config.headers.Authorization = token
```

所以现在所有的路由都会带上Authorization但是只有use了鉴权中间件的才会验证JWT有效性。

HTTPS的对称/非对称加密或者说TLS层的实现：

对称加密：双方使用相同的加密规则加密

非对称加密：既定规则就是公钥加密的东西只能用私钥解开。

1. 你的浏览器生成一个**随机的临时密钥**（比如 `6f8d9a...`）。 也成为***会话密钥***也就是规则假如：“往右移1位”
2. 你用**服务器的公钥**把这个临时密钥加密，发给服务器。
3. 服务器用**自己的私钥**解密，得到你的临时密钥。
4. 从此，双方都用这个**临时密钥**进行对称加密通信（速度快）。

但是这里是有一个中间人攻击的问题的：我怎么知道我获取的公钥就是我想访问的服务器的公钥？高级的黑客可以拦截你的请求，说“我就是baidu.com 我的公钥是xxx”，客户端不知道假百度，所以就用假公钥加密了会话密钥，黑客用假私钥解开得到会话密钥，再用百度的真公钥加密会话密钥返回给百度。这样 我确实和真百度约定好了往右移1位，但是黑客也知道了我和百度后续的对称加密方式。
怎么解决？升级为CA证书。
我不再直接请求公钥，而是请求CA证书（公钥+CA数字签名）。百度服务器向CA机构申请CA证书，这个CA证书是由CA机构的私钥签名的，存放在百度服务器上，我怎么判断我收到的证书是否合规？那就是我用我设备上预存的CA公钥解密证书，如果解密成功就是CA机构的官方证书，否则就是假证书。
